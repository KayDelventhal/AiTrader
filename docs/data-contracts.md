# Data contracts

API prefix: `/api/v1`. Request models reject unknown fields. Public responses use explicit Pydantic schemas, including discriminated backtest/research job results, and carry `schema_version` where appropriate. Errors provide HTTP status, a stable `code`, safe `detail`, `request_id` and optional validation locations/codes; submitted values are omitted. Frontend response types are generated from OpenAPI and checked for drift.

- Instrument IDs begin with `DEMO_` and have no broker mapping. Display tickers are not used as external identities.
- Bars contain UTC epoch seconds for charts, aware ISO availability timestamps, OHLCV, final=true and revision=1. They come from a seeded fixture generator, never a fallback.
- Existing demo event evidence records have IDs, publishers, availability timestamps, revision, copy count, original-source count, and a fictional marker. Their event details distinguish scenarios/hypotheses from observations. Genuine gathered source documents use separate contracts and are not inserted into these fixture events.
- A strategy version stores its formal SMA parameters, hypothesis, instrument, whole-share size, execution costs and optional horizon (`intraday`, `days_weeks`, `weeks_months`). Newly saved versions resolve an omitted horizon from the workspace default. Existing versions without a horizon remain unspecified; they are not backfilled from current settings. Saving a modification inserts a new row.
- A backtest result records engine/version, snapshot hash, strategy-version ID, orders with separate signal/fill times, equity, cost sensitivity, assumptions and limitations.
- New queued jobs persist a frozen input payload, snapshot version, canonical SHA-256 digest, capture time, workspace settings/revision and horizon. Backtests capture saved strategy inputs and bars; research captures the instrument, cutoff and eligible evidence/event state. Workers verify the digest before computation. Compact job views omit the large payload; `/jobs/{id}/snapshot` exports it only to the run owner. Older completed jobs remain readable as legacy runs; jobs without verified captured inputs cannot export or reconstruct them from current data.
- Account cash, cost basis, realized P&L, proposal prices and fees are decimal strings. Positions are whole shares. This first ledger uses JSON position values inside the transactionally updated account row.
- Proposal fingerprints hash every canonical payload field. Account revision is part of the payload; changes require a new proposal. Repeated approval of an already-filled identical proposal returns the same fill.
- Replay requests filter displayed market bars/indicators, event availability, research input and annotations on the server. This is chart replay, not yet a fully isolated historical training context: all surrounding workspace data and tools still need consistent cutoff enforcement. Account ledger replay is not implemented; the terminal explicitly says replay does not change the account.

## Workspace settings and costs

- `/workspace/settings` exposes the shared markets, horizon, monthly EUR allowance, warning threshold and revision. Updates require owner authorization, CSRF and the expected revision. Each successful change appends a settings revision and audit event. Settings changes apply to future defaults while captured strategy/run settings remain immutable.
- The initial markets are `US` and `EU`, the horizon is `days_weeks`, and the monthly allowance is EUR 20. These values configure intended coverage and workflow; actual market data remains fictional daily bars.
- Calendar months use Europe/Berlin boundaries; stored timestamps remain timezone-aware UTC. A `BudgetMonth` preserves its allowance and settings revision. Changing the allowance updates the current month and future default, not an already elapsed month.
- `/costs` exposes confirmed expenses, estimates, reservations, unresolved prior-month holds, remaining/available allowance, status, category/provider breakdowns, recurring commitments and entry history. Missing cost is `null` with an unknown state, never a free charge. Unknown costs block new reservations even when a numeric remainder exists.
- Cost categories are `AI`, `SEARCH_NEWS` and `MARKET_DATA`. Entries distinguish `RESERVED`, `UNCERTAIN`, `ESTIMATED`, `CONFIRMED` and `CANCELLED`, with source `manual`, `reservation` or `recurring`. Original currency/amount, dated FX basis, pricing version and optional owned run/strategy references are retained. EUR conversion uses Decimal and integer micro-EUR storage, rounded conservatively at that precision; API amounts are decimal strings.
- `/costs/entries` records manual expenses. `/costs/reservations` admits a bounded maximum only when the shared allowance permits it. Mutation services serialize their balance reads and writes within a short SQLite transaction. Unknown prior charges and unresolved prior-month bounds cannot silently disappear at a month boundary.
- `/costs/{id}/reconcile` requires an expected revision and event key. Creation and reconciliation keys are idempotent for the same request and conflict if reused for different values. Revisions retain prior amounts/status/provenance. Estimated usage retains any unconsumed reservation bound; confirmation releases the hold. An ambiguous timeout retains uncertainty instead of being treated as free. Corrections record actual invoices even above the ceiling and thereby block subsequent paid admission.
- `/costs/recurring` records an explicit EUR monthly commitment, materialized once per month. The stop action ends future local renewals and preserves the current month's commitment. Neither action creates or cancels a provider subscription. Bills reconcile through the same entry-history path.
- `/performance/cost-impact` separates private local-demo realized and unrealized P&L from shared operating expenses. Its optional net figure subtracts the full workspace confirmed/estimated expenses from this account's realized demo P&L, clearly labelled `FULL_WORKSPACE_SCENARIO`; reservations are not incurred expenses and execution fees are not deducted twice. No live performance is available. Unknown costs or an invalid reconstructed ledger leave the net figure unavailable.
- `/jobs/{id}/costs` reports attributed cost records for an owned run. Shared research remains charged once; no automatic strategy allocation or attribution of trading success to AI is inferred.

Paid-provider activation and usage/billing adapters remain disconnected. Public-feed collection has a separate explicit capability and does not use a paid model. These ledger controls apply to recorded costs and reservations; they do not independently guarantee an external provider's invoice total or account-wide spending outside the app.

## Research gathering and source history

- `/gathering/config` exposes versioned shared settings, domains, configured sources, the fixed public-source catalog, owner-edit capability and runtime network permission. The initial editable domains are Nvidia, Amazon, Macroeconomics and Geopolitics. Domains store descriptions, keyword/entity vocabulary, active state and revision. Keywords currently describe research interests; they are not an LLM classifier or a feed-item rejection filter.
- `/gathering/settings`, `/gathering/domains` and `/gathering/sources` require owner authorization and CSRF for writes. Updates require the expected revision. The catalog contains NVIDIA newsroom, AWS news blog, Federal Reserve monetary policy, ECB press, Council of the EU press and EIA Today in Energy. A catalog source is configured once and can cover several domains. Arbitrary feed endpoints are not accepted.
- Collection requires the process public-feed capability, the persisted workspace toggle, the individual source toggle and at least one active assigned domain. Source assignments retain inactive domain IDs, while new run snapshots contain only active domains. Existing document/run scope is preserved. Manual historical imports can explicitly refer to inactive domains.
- A source records its interval, next due time, last check/success/error and active run ID. The allowed interval is 15 to 10,080 minutes. `/gathering/sources/{id}/collect` queues manual work; duplicate requests return the active run, and completed manual requests have a one-minute cooldown. The local scheduler coalesces missed intervals. A stored enablement setting does not imply that a request succeeded or that the computer is continuously running.
- `/gathering/runs` exposes the most recent runs. Each retains source/catalog URL identity, source/settings revisions and domain snapshots, trigger, actor, timestamps, status, outcome counts and retrieval metadata. Status is `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED` or `CANCELLED`. HTTP/parser metadata includes response hash, skipped/truncated item information and explicit zero model calls. One run can add no new documents because all entries are unchanged.
- Documents have stable source-scoped publication identities. RSS uses configured source plus canonical publication URL; manual imports use their own publication namespace. Identical stored content/context does not create another revision. Changed content or captured attribution creates a new revision; a reversion is still a new observed revision. This is not semantic deduplication across publishers or proof of independent sources.
- A document revision preserves title, normalized source text/excerpt, URL, publisher, parsed source fields including raw dates, domain snapshots, attribution, content hash and import note. Feed article links are references only; the collector does not fetch full article pages or infer verified market events. Existing fixture research jobs continue to read fictional events.
- `published_at` is an aware publisher timestamp where available. `published_on` records a calendar date when a manual historical source establishes no exact time; the two fields are mutually exclusive. Missing dates stay null. `occurred_at` is a separate optional importer-supplied event time. `first_seen_at` and each revision's `recorded_at` are actual app observation/storage times. `available_at` is at least the recorded time, and conservatively respects a later exact publisher timestamp. Historical imports never make the app appear to have known material before it was imported.
- `/gathering/imports` accepts a bounded manual source excerpt with publisher, HTTPS URL, domain assignments, date precision and provenance note. It does not fetch the URL or authenticate the publication. Idempotency keys return the same outcome for the same request and reject different input under an existing key. Older payloads without `published_on` remain readable; absence and null do not cause false revisions.
- `/gathering/documents` performs SQL filtering and pagination by domain, source, stored text, publication range and optional `known_by` cutoff. It first selects each document's latest eligible revision, then filters its content/domain state; old matching versions cannot leak into a current view after a correction. Exact publication ranges use UTC instants; date-only records match calendar days without claiming intraday precision. Unknown publication dates remain explicit and do not match a publication-date filter.
- `/gathering/documents/{id}` returns the selected document and visible revision history. With `known_by`, later revisions are excluded from detail and export. This reconstructs the application's stored-source knowledge; it does not prove the exact historical public availability of a newly imported archive or remove future knowledge from an LLM.

Full listing identity, dataset/Parquet tables, synthesized event/correction/retraction ingestion, advanced source-retention policy, order state machine, trading FX snapshots, complete historical training isolation and fully inferred client route/request bindings remain on the TODO list.
